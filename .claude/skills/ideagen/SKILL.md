Read the **English** `aris-profile/PROFILE_AUTO.md` (via `$ARIS_PROFILE`) first — canonical; `PROFILE_AUTO.zh.md` is a human-facing mirror, not for logic. If it is absent, tell the user to run `/profile-construct`. Converse in **Chinese**; keep code/identifiers/paper-titles native.

**Arguments:** `<direction>` (free text) · `— lens: engineering|theory|benchmark` (= **mode**) · `— ref paper: <arXiv URL | PDF | URL>` (*optional*, triggers A0).

## Step 0 — Lock MODE + direction first
The mode decides what *kind* of idea is generated, so fix it BEFORE anything else — never infer silently. If `— lens:` was passed use it; else **AskUserQuestion** for the mode (engineering = iterate habitual methods, reuse code · benchmark = survey / new dataset-eval / reproduce-and-beat · theory = a hypothesis/bound on the method-evolution fault line) and confirm `<direction>` at the same time (offer her *Niche subfields* if none given). Only once both are fixed do A0/A1/A2 run.

## Output conventions
- **One folder `outputs/` (create it), two-digit step prefixes.** The survey `outputs/01_LIT_SURVEY.html` is written by `/research-lit` (the grounding this skill reads). This skill writes `outputs/00_REF_PAPER_SUMMARY.html` (only with `— ref paper:`) and the canonical `outputs/02_IDEA_REPORT.html` (a **short** landscape pointer to the survey + the ranked ideas — NOT a duplicated paper appendix). Downstream continues the numbering (`03_EXPERIMENT_PLAN` … `05_FINDINGS`).
- **Every deliverable is self-contained HTML, never Markdown** — inline `<style>`, no external assets, real structure (`<h1>/<h2>`, `<table>`, `<ul>`). **Every paper reference is a direct `<a href>`** to its arXiv/DOI; unverifiable → visible `pending`, never a fabricated URL.
- **Output language follows the user (global language policy — never hard-coded).** Write the report in the language the user asked for (a `— lang:` directive, else the language of their request; if ambiguous, ask). That single file `outputs/02_IDEA_REPORT.html` is the **primary** — it is what `/workplan` reads, and the `SELECTED` stamp lives in it (downstream parses ids/structure, not prose, so any language works). Same for `00_REF_PAPER_SUMMARY.html`. Produce a second-language mirror `outputs/02_IDEA_REPORT.<lang>.html` **only if the user wants both**; a mirror must be a faithful native translation (same structure, links, ids, scores; keep code/paper-titles native). Write natively, never word-for-word machine translation; re-read each sentence. **Address the researcher in the SECOND person** (你/你的 in Chinese, "you/your" in English), never the third person.

## A0 — Reference paper (only if `— ref paper:` given)
Summarize BEFORE surveying so generation targets its gaps. Fetch (`tools/fetch_fulltext.py` / `pdftotext` / WebFetch), then write `outputs/00_REF_PAPER_SUMMARY.html`: **what they did · key results · limitations & open questions · improvement directions**. Numbers/claims trace to the paper's text; if you couldn't fetch it, say so and ask for the PDF.

## A1 — Read the literature survey (from `/research-lit` — do NOT re-survey)
**ideagen no longer runs its own survey.** The grounding is the survey `/research-lit` already produced at **`outputs/01_LIT_SURVEY.html`**. Do this:
1. **Read `outputs/01_LIT_SURVEY.html`.** Extract its landscape prose, the live debates, the **structural gaps** it flagged, and its verified paper list (titles + arXiv ids + one-line takeaways) — this is the evidence base the ideas are grounded on.
2. **If it is missing or clearly off-topic vs the locked `<direction>`** (e.g. the survey covers a different topic than the researcher just asked for), do NOT silently proceed on nothing: **run `/research-lit "<direction>" — for: ideagen`** to produce it first (fan-out verified search, writes the white-bg Chinese HTML), then read it. If the researcher explicitly asked to skip the survey, proceed on the profile alone and say the grounding is thin.
3. **Do NOT duplicate the survey's appendix in the idea report.** The full categorized paper list lives in `01_LIT_SURVEY.html`. In `02_IDEA_REPORT.html`, open with a **short Literature Landscape** (a few sentences summarizing the survey's debates + gaps) that **links to `01_LIT_SURVEY.html`** ("完整证据清单见文献综述"), and per idea cite only the **closest 1–3 papers** (direct `<a href>`) needed to justify its novelty verdict. **Anti-hallucination still applies:** cite only papers that appear (verified) in the survey or that you separately retrieved for a novelty check; unverifiable → `[UNVERIFIED]`, never fabricate.
4. **Novelty top-ups are allowed.** A2/A3 may run a few *targeted* searches to pin the closest concurrent work for a specific candidate (last 3–6 months) — that is a novelty check, not a re-survey. Keep it narrow.

## A2 — Idea generation (ONE lens, method-first)
Generate 6–8 candidates through the chosen mode, seeded by the profile AND the survey's structural gaps (from A1 / `01_LIT_SURVEY.html`):
- **engineering** — iterate habitual methods from *Dominant Methods*; prefer reuse-existing-code. No arbitrary time cap ("2-week pilot"); let the problem set the scope.
- **theory** — read *Publications Index* in time order + *Research Lineage*; find the method-evolution fault line; propose hypotheses adjacent to, not repeating, the lineage.
- **benchmark** — from *Active Venues* + *Niche Subfields*: follow-up **survey** / **custom benchmark-dataset** filling an eval gap / **reproduce-and-beat** a recent competitor.

**One-sentence lead + method-first.** Every idea opens with **ONE clear sentence** that says what it is — concrete about mechanism and contribution, readable in a single pass. Write it **for an experienced peer**: use the correct domain terms precisely (do not avoid them), but do NOT hide behind abstract methodology-speak ("steering as a measurement tool for mechanistic faithfulness") NOR dumb it down with childish analogies (kids arguing about vaccines). If the one sentence isn't clear, the idea isn't ready. Only *after* that sentence give the **2–4 concrete method steps** (what we build/train/run), then hypothesis/expected-outcome as acceptance criteria.

**Re-run = accumulate, never discard.** A re-invocation does NOT replace the prior slate with an all-new one. Read any prior `outputs/02_IDEA_REPORT.html`, **carry ALL its ideas forward** (they remain valid candidates — an un-selected idea is not a failed idea), then **ADD fresh candidates** by rotating to a different profile asset / gap, and **re-rank the union**. The pool grows across runs. Mark the new ones (`🆕 new this run`) so the researcher sees what changed. Only drop an idea the researcher *explicitly rejected* as a direction. Do NOT manufacture a gimmicky twist / far-fetched mashup / contrived problem just to add something new: if this run's honest fresh angles turn out crowded or weaker than the carried-forward ideas, say so explicitly and let the strong prior ideas keep their rank rather than padding the slate.

**≥2–3 of the slate must be `novel` (not just `differentiable`)**, else too few real options. If short, keep widening (new gap × new asset) until you reach it — but never fake the count or mislabel `differentiable` as `novel`; if honest widening truly can't reach it, present what you have and say so.

## A3 — Novelty check (annotate, do not narrow)
Per surviving candidate: (1) **vs her OWN work** — flag anything that merely restates a paper she published; (2) **vs the field incl. last 3–6 months** — record closest paper + differentiation point. Verdict `novel` / `differentiable (needs framing)` / `already exists`; unverifiable → `[UNVERIFIED]`. This is an **annotation** — only a genuine exact duplicate is dropped here; quality narrowing happens at A4 + the human gate, never by silent deletion.

## A4 — Objective gate · scorecard · devil's-advocate ranking
Separate the objective filter from the subjective ranking; the generator's taste does NOT do the quality narrowing (borrowed from autoresearch).
1. **Objective gate (mechanical only):** drop a candidate only on an objective fact — compute clearly beyond the profile's hardware, or a provably-unavailable dataset. Never drop on "looks complex" / "might already be done" (annotate instead).
2. **Scorecard per idea** (transparent, reproducible): **Novelty** `X/10` + closest work + differentiation · **Feasibility** (compute/data/impl vs the profile stack) · **Risk** LOW/MED/HIGH · **Contribution type** (empirical / method / benchmark / theory / diagnostic) · **Fit** (which *Dominant Method*/niche) · **Single-mechanism test** (below) · **Reviewer's likely objection** (strongest top-venue objection) · **rough effort** (honest).
2a. **Single-mechanism test — the anti-"boring mashup" gate (apply to EVERY idea).** State the idea's ONE core mechanism in a single sentence, then try to break the idea into independent contributions. **If it decomposes into "improvement A + improvement B" (e.g. `technique X` *plus* `apply it to domain Y`), where each half is a separate increment a reviewer could accept or reject on its own, the idea has no single core — it is a boring mashup and must NOT ship in that form.** Fix it, don't pad it: reforge around one insight so the parts stop being separable — the second "contribution" should become a *consequence or a falsification test* of the first, not a bolt-on module. (E.g. "defense A + also works on audio" is a mashup; "harmful intent lives on one modality-invariant axis, so the same conditional defense transfers to audio *for free* — and if it needs a separate audio module, the core claim is false" is one mechanism whose audio result is the test of the claim, not a second feature.) A candidate that survives only as A+B gets **capped at `differentiable`, never `novel`**, and is downranked below any true single-mechanism idea; note the decomposition explicitly in its card so the human sees why. This is *not* a licence to invent a grand unifying theory over a genuinely engineering idea — the reforged core can be a concrete engineering mechanism — it just has to be ONE thing.
3. **Devil's-advocate ranking:** run one adversarial pass over the full set (strongest objection · likely failure mode · **does it pass 2a or is it an A+B mashup** · real collision or differentiable · how to rank for a top venue · which 2–3 to actually work on) and **rank by that verdict, not first-pass enthusiasm.** Prefer a **cross-model** reviewer — send the set to `codex` via `mcp__codex__codex` — else an explicit same-model pass (write the objections out; never skip).

## GATE — human is judge
Present **5–7 ranked ideas** in `outputs/02_IDEA_REPORT.html` in A4 rank order (ranked `<table>`), **≥2–3 with a `novel` verdict**. Give each a stable id `I1, I2, …` in the first column (this is how the pick is referenced downstream). **Each idea — in both the table and its card — leads with its A2 one-sentence pitch** (peer-level, concrete, no jargon-fog / no childish analogy); the card then adds its A4 scorecard plus method steps · hypothesis · MVE · why-novel-vs-own-work. The AskUserQuestion options must use that same one-sentence pitch, not a vaguer paraphrase. **Stop. AskUserQuestion for the researcher to pick / kill / redirect** (offer ideas by id + one-line title). Never auto-proceed.

**Persist the pick:** after she picks, stamp `outputs/02_IDEA_REPORT.html` — a top banner `Selected: I<k> — <title>` (with date) + a `✅ SELECTED` tag on that row. If she redirects instead, regenerate and leave no stale stamp.

**Handoff:** the chosen idea → **`/workplan`**, which reads the stamp and writes `outputs/03_EXPERIMENT_PLAN.html`. Do not write the experiment plan here.
